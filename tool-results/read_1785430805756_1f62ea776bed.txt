   147→# Expert Panel Findings — Himal Commerce Audit (expert-5)
   148→
   149→## QA Engineer findings
   150→
   151→### QA — 1. Zero automated tests in the entire codebase
   152→- **Severity**: P0
   153→- **Impact**: Every deploy is a leap of faith. The features-1 refactor rewrote checkout
   154→  (atomic inventory, payment status semantics, variant handling) with no regression
   155→  coverage — the next deploy could silently reintroduce the oversell bug and nobody
   156→  would know until a customer complains.
   157→- **Where**: missing entirely. `package.json` has no `test` script; `tests/` contains
   158→  only leftover shell scripts (`python-runtime-build.sh`, `database-runtime-build.sh`,
   159→  `python-runtime-container.sh`) unrelated to this project. No vitest/jest/playwright/
   160→  cypress/@testing-library in dependencies.
   161→- **Fix**: Add `vitest` + `@testing-library/react` + `@playwright/test` to devDeps.
   162→  Add `scripts/test: "vitest run"`, `scripts/test:e2e: "playwright test"`,
   163→  `scripts/test:ci: "vitest run --coverage"`. Create `tests/unit/` (cart-store logic,
   164→  slug generator, NPR formatting, shipping calc), `tests/api/` (route handlers with
   165→  prisma mock), and `tests/e2e/` (checkout smoke, admin CRUD). Minimum viable suite:
   166→  `tests/unit/cart-store.test.ts`, `tests/api/checkout.test.ts`,
   167→  `tests/e2e/checkout.spec.ts`, `tests/e2e/multi-tenant.spec.ts`.
   168→
   169→### QA — 2. Multi-tenant isolation leak on detail endpoints
   170→- **Severity**: P0
   171→- **Impact**: Any visitor can read or modify any other store's orders/products by
   172→  guessing/enumerating IDs. `GET /api/orders/[id]` returns the order with no
   173→  `storeId` filter; `PATCH /api/orders/[id]` lets anyone flip payment status, cancel
   174→  orders, or change shipping info across tenants. Same for `/api/products/[id]`
   175→  PUT/DELETE (delete a competitor's product) and `/api/customers/[id]` if added later.
   176→- **Where**: `src/app/api/orders/[id]/route.ts:7-36` (GET/PATCH/DELETE — no storeId
   177→  check anywhere), `src/app/api/products/[id]/route.ts:26-147` (GET/PUT/DELETE —
   178→  same), `src/app/api/categories/[id]/route.ts:7-85`.
   179→- **Fix**: Every `[id]` route must accept `storeId` (query param or body) AND verify
   180→  ownership:
   181→  ```ts
   182→  const order = await db.order.findUnique({ where: { id } })
   183→  if (!order || order.storeId !== storeId) {
   184→    return NextResponse.json({ error: 'Not found' }, { status: 404 })
   185→  }
   186→  ```
   187→  Add `tests/api/tenant-isolation.test.ts` covering: store A cannot GET/PATCH/DELETE
   188→  store B's order, product, category. Once real auth lands, replace `storeId` param
   189→  with session-derived storeId.
   190→
   191→### QA — 3. No error boundary — unhandled runtime errors crash the whole SPA
   192→- **Severity**: P1
   193→- **Impact**: A single React render error in any admin component (e.g., a malformed
   194→  product from the DB) takes down the entire client-side app with a white screen and
   195→  no recovery path — the user has to hard-refresh and hope. Since routing is hash-based
   196→  on a single `page.tsx`, there's no route-level error isolation at all.
   197→- **Where**: missing entirely — no `src/app/error.tsx`, no `src/app/global-error.tsx`,
   198→  no `ErrorBoundary` wrapper around `<Admin>`/`<Storefront>`/`<Platform>` in
   199→  `src/app/page.tsx:46-52`.
   200→- **Fix**: Add `src/app/error.tsx` (App Router root error boundary, server component
   201→  shell with a client reset button) and `src/app/global-error.tsx` (catches root
   202→  layout errors). Wrap each top-level view in a React error boundary component
   203→  (`src/components/error-boundary.tsx`) so a storefront crash doesn't take down the
   204→  admin and vice versa.
   205→
   206→### QA — 4. TypeScript checking disabled in build
   207→- **Severity**: P1
   208→- **Impact**: `next.config.ts` sets `typescript.ignoreBuildErrors: true`, so `next
   209→  build` succeeds even with type errors. Combined with no `tsc --noEmit` in CI, type
   210→  regressions ship to production silently. `tsconfig.json` also sets
   211→  `noImplicitAny: false` despite `strict: true`, weakening the safety net further.
   212→- **Where**: `next.config.ts:6-8` (`ignoreBuildErrors: true`, `reactStrictMode: false`),
   213→  `tsconfig.json:13` (`noImplicitAny: false`).
   214→- **Fix**: Remove `typescript.ignoreBuildErrors` from `next.config.ts` (or set to
   215→  `false`). Set `noImplicitAny: true` in tsconfig. Add `"typecheck": "tsc --noEmit"`
   216→  to package.json scripts and run it in CI (see Automation finding 1). Fix any
   217→  resulting type errors — they're bugs waiting to happen.
   218→
   219→### QA — 5. Checkout creates order BEFORE atomic inventory decrement (orphan orders on race)
   220→- **Severity**: P1
   221→- **Impact**: The code checks inventory, creates the order + OrderItems, THEN runs the
   222→  atomic `updateMany WHERE inventory >= qty`. If the decrement fails (concurrent
   223→  orders stole the last units), the order is already in the DB with a `[SYSTEM]
   224→  Inventory race detected` note appended — but it's a real, customer-visible order
   225→  that can never be fulfilled. There's no automatic cancellation, no refund trigger,
   226→  no merchant notification. The "best-effort compensation" comment at line 207 is
   227→  aspirational; no inventory is actually restored.
   228→- **Where**: `src/app/api/checkout/route.ts:146-216`. Order created at line 146,
   229→  decrement loop at 190-204, failure handling at 206-216 only writes a note.
   230→- **Fix**: Wrap the whole thing in `await db.$transaction(async (tx) => { ... })`.
   231→  Do the conditional decrement FIRST inside the transaction; only create the order
   232→  if all decrements succeed. On any `count === 0`, throw to roll back and return 409.
   233→  Test: `tests/api/checkout-concurrency.test.ts` — fire 5 parallel checkouts for the
   234→  last unit of a product, assert exactly 1 succeeds and 4 get 409.
   235→
   236→### QA — 6. No variant edge-case coverage (out-of-stock, deleted variant in cart, price drift)
   237→- **Severity**: P1
   238→- **Impact**: The cart is persisted in `localStorage` (`himal-cart` key in cart-store).
   239→  If a customer adds variant "Red / Large" today, comes back next week, and the
   240→  merchant has since deleted that variant (PUT /api/products/[id] with `_destroy`),
   241→  the checkout will hit the `Variant not found` branch at line 100 and 500-ish fail
   242→  with a generic message — the customer has no idea which item is the problem.
   243→  Same UX failure if the variant went out of stock (0 left) or the price changed
   244→  since they added it (client price is now stale, but server re-fetches so it's
   245→  actually fine — except the order total surprises the customer).
   246→- **Where**: `src/app/api/checkout/route.ts:97-101` (variant lookup + generic 400),
   247→  `src/lib/cart-store.ts:25-106` (persisted cart with no expiry/staleness check),
   248→  `src/components/storefront/checkout-modal.tsx:112-119` (sends stale `price` from
   249→  localStorage).
   250→- **Fix**: (a) On checkout failure, return a structured error like
   251→  `{ error: '...', code: 'VARIANT_UNAVAILABLE', productId, variantId }` so the modal
   252→  can highlight the offending line. (b) Compute the order total server-side from
   253→  `productMap` and return the corrected total to the client for re-confirmation when
   254→  it differs by >1% from the client-sent total. (c) Add
   255→  `tests/api/checkout-variants.test.ts` covering: deleted variant → 400 with code,
   256→  out-of-stock variant → 409, variant from wrong product → 400, variant inventory
   257→  exactly equal to requested qty → success.
   258→
   259→### QA — 7. No payment-status transition validation
   260→- **Severity**: P1
   261→- **Impact**: `PATCH /api/orders/[id]` accepts any string for `paymentStatus` and
   262→  `status` — no enum check, no transition rules. A merchant (or attacker via finding
   263→  QA-2) can flip `paid` → `unpaid` → `paid` → `refunded` with no record, mark a
   264→  cancelled order as `delivered`, or set `paymentStatus: 'banana'` and corrupt the
   265→  row. The admin UI at `orders.tsx:289` only toggles paid/unpaid but the API
   266→  accepts anything.
   267→- **Where**: `src/app/api/orders/[id]/route.ts:17-29` (PATCH accepts any value),
   268→  no enum validation anywhere. `Order.paymentStatus` comment at schema.prisma:178
   269→  lists allowed values but they're not enforced.
   270→- **Fix**: Add a zod schema:
   271→  ```ts
   272→  const statusEnum = z.enum(['pending','processing','shipped','delivered','cancelled'])
   273→  const payEnum = z.enum(['unpaid','pending','paid','refunded'])
   274→  const transitions: Record<string, string[]> = {
   275→    unpaid: ['pending','paid'], pending: ['paid','unpaid'], paid: ['refunded'],
   276→    refunded: []
   277→  }
   278→  ```
   279→  Reject invalid transitions with 409. Log every transition to the AuditLog (see
   280→  Data finding 3). Test: `tests/api/order-transitions.test.ts`.
   281→
   282→### QA — 8. ESLint config disables every meaningful rule
   283→- **Severity**: P2
   284→- **Impact**: The ESLint config at `eslint.config.mjs:9-45` turns OFF
   285→  `no-explicit-any`, `no-unused-vars`, `no-unreachable`, `no-console`,
   286→  `react-hooks/exhaustive-deps`, and 15+ other rules. `eslint .` runs but catches
   287→  almost nothing — dead code, console.logs in production, unreachable branches, and
   288→  missing effect deps all ship silently. This makes the lint step in CI (when added)
   289→  nearly worthless.
   290→- **Where**: `eslint.config.mjs:10-45`.
   291→- **Fix**: Re-enable the core rules. Keep `no-explicit-any: 'warn'` (not error) for
   292→  pragmatism, but turn `no-unused-vars`, `no-unreachable`, `no-console` (allow
   293→  `console.warn`/`console.error`), and `react-hooks/exhaustive-deps` back to
   294→  `'warn'` or `'error'`. Run `eslint . --fix` once to clean up the resulting noise,
   295→  then enforce in CI.

   299→### Data — 1. No AnalyticsEvent model — zero funnel / conversion tracking
   300→- **Severity**: P0
   301→- **Impact**: There is no way to answer "how many storefront visitors added to cart?"
   302→  or "what's our checkout conversion rate?" or "which product page has the highest
   303→  bounce?" The `/api/stats` dashboard reports orders + revenue but nothing about the
   304→  top of the funnel (page views, add-to-cart, checkout-started, checkout-abandoned).
   305→  Merchants are flying blind on conversion optimization.
   306→- **Where**: missing entirely. `prisma/schema.prisma` has Store/Product/Order/Customer
   307→  but no `AnalyticsEvent` (or `PageView`/`CartEvent`/`CheckoutEvent`) model. No
   308→  event-tracking call in `src/components/storefront/*` or `src/app/api/checkout`.
   309→- **Fix**: Add to schema.prisma:
   310→  ```prisma
   311→  model AnalyticsEvent {
   312→    id        String   @id @default(cuid())
   313→    storeId   String
   314→    store     Store    @relation(fields: [storeId], references: [id], onDelete: Cascade)
   315→    type      String   // page_view | product_view | add_to_cart | checkout_start | checkout_complete | checkout_abandon
   316→    sessionId String
   317→    userId    String?  // customer id if known
   318→    productId String?
   319→    variantId String?
   320→    cartValue Int?     // paisa snapshot at event time
   321→    meta      Json     // flexible: { source: 'search'|'category'|'home', ... }
   322→    createdAt DateTime @default(now())
   323→    @@index([storeId, type, createdAt])
   324→    @@index([sessionId])
   325→  }
   326→  ```
   327→  Add `POST /api/events` route. Fire events from `product-detail-drawer.tsx`,
   328→  `cart-drawer.tsx`, `checkout-modal.tsx`. Build a funnel widget on the dashboard
   329→  showing page_view → product_view → add_to_cart → checkout_start → checkout_complete
   330→  with conversion % between stages.

   342→  (or xlsx via the `exceljs` package). Add an "Export" button to each admin table
   343→  header that calls these endpoints. CSV columns for orders: orderNumber, createdAt,
   344→  customerName, customerPhone, shippingDistrict, status, paymentMethod,

   346→  Test: `tests/api/export-orders.test.ts` verifies UTF-8 BOM (Nepali characters),

   349→### Data — 3. No audit log — who changed what, when, is unknowable
   350→- **Severity**: P1
   351→- **Impact**: In a multi-tenant SaaS, merchants need to trust that platform staff or
   352→  their own employees can't silently change prices, mark orders paid, delete products,
   353→  or modify settings without a trace. Today, a staff member could mark their own
   354→  order as `paid` then `refunded`, change a product price, and delete the evidence —
   355→  with zero record. This is a trust and compliance blocker for any merchant beyond
   356→  hobbyist use.
   357→- **Where**: missing entirely. No `AuditLog` model in `prisma/schema.prisma`. No
   358→  logging in any PATCH/PUT/DELETE handler (`/api/orders/[id]`, `/api/products/[id]`,
   359→  `/api/stores/[id]`, `/api/categories/[id]`).
   360→- **Fix**: Add to schema.prisma:
   361→  ```prisma
   362→  model AuditLog {
   363→    id        String   @id @default(cuid())
   364→    storeId   String?
   365→    actorId   String?  // user id when auth exists
   366→    actorKind String   @default("anonymous") // anonymous | user | system | cron
   367→    action    String   // order.update | product.delete | store.update | ...
   368→    entityType String  // order | product | category | store | customer
   369→    entityId  String
   370→    before    Json?
   371→    after     Json?
   372→    ip        String?
